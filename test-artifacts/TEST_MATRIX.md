### BUG-01 (развёрнуто)
- **Steps:** 1) Оформить подписку, ввести токен. 2) Добавить бота в канал как админа (права подтверждены в Telegram). 3) Нажать «Бот добавлен».
- **Expected:** `GET /telegram-channels` возвращает канал; либо при пустом ответе — empty/error-state + retry; переход на 2/3 возможен.
- **Actual:** API `200 OK` с телом `{type:"result", data:[]}` при подтверждённом админстве; UI не даёт feedback и блокирует переход.
- **RCA (5 Whys):** гипотеза «мёртв сервис синхронизации» **снята действием** (контейнер поднят, бот пингуется — дефект воспроизводится) → точка сбоя = контракт API↔UI / отсутствие записи привязки в БД (бэк не опрашивает Telegram Bot API о реальном админстве).
- **Impact:** платный пользователь не может активировать купленную функцию → риск оттока и тикетов на самой дорогой точке воронки.

### BUG-02 (развёрнуто)
- **Steps:** 1) Привязать бот токеном. 2) Искать в UI кнопку замены/удаления токена.
- **Expected:** доступна понятная операция «Заменить/Удалить токен» без создания нового аккаунта.
- **Actual:** элемент не обнаружен; путь исправления ошибочного токена неочевиден.
- **Impact:** пользователь с ошибочным токеном застревает → тикет в поддержку.

### BUG-03 (развёрнуто)
- **Предусловие (честно):** карта без достаточных средств → CloudPayments отклоняет платёж (decline / insufficient funds). Воспроизведено именно в этом негативном сценарии; реальной оплаты для тестового не требуется.
- **Steps:** 1) Экран оформления подписки (CloudPayments). 2) Данные карты без средств. 3) Подтвердить оплату.
- **Expected:** decline обработан сквозным контрактом: бэк возвращает 4xx с кодом (`card_declined` / `insufficient_funds`); фронт показывает соответствующее сообщение и подсказку (другая карта / пополнение); в консоли нет 5xx; битая подписка не создаётся.
- **Actual (рассинхрон бэк↔фронт):** бэк возвращает `500 Internal Server Error` на `POST /subscription/create-cloudpayments` (отказ провайдера проброшен как необработанное исключение); фронт при этом показывает fallback «Недостаточно денег на карте» + кнопку «Повторить». Пользовательский путь формально не сломан, но контракт нарушен.
- **Итерация гипотез (RCA):** первичная гипотеза «пользователь в тупике» **опровергнута проверкой UI** (фронт показывает fallback) → уточнено до рассинхрона бэк/фронт + маскировки 500. Корень на бэке: коды отказа провайдера не замаплены на клиентский 4xx.
- **Граница ответственности:** `500` получен с `api.chatplace.io` (собственный бэк), а не от CloudPayments. Внешний ответ провайдера из браузера не виден (сервер-сервер вызов) и не оценивается — мы не сваливаем на третью сторону. Decline как событие — вне зоны (не влияем); обработка этого события на нашем бэке — в зоне (влияем).
- **Open question (не обвинение, уточнение контракта):** если 500 на decline intentional (осознанная маскировка деталей провайдера) — зафиксировать как архитектурное решение и пересмотреть DoD/алёртинг; если нет — чинить маппинг кодов отказа на 4xx. В обоих случаях текущее поведение нарушает семантику HTTP (RFC 9110: 5xx = неожиданная серверная ситуация, а decline — штатный исход) и Definition of Done.
- **Сопутствующий риск (мислид):** если фронт отображает «недостаточно средств» на *любой* 500 от этого эндпоинта, то при реальном падении сервера пользователь получит то же сообщение и будет менять карту вместо ожидания восстановления — требует проверки, различает ли фронт типы ошибок.
- **UX-неточность копии:** «Пожалуйста, повторите попытку позже» противоречит «недостаточно средств» (повтор позже не поможет при отсутствии средств).
- **Доп. проверки (отделить причины):** карта со средствами (happy path) и карта с истёкшим сроком / неверным CVC — если 500 только при decline, корень = необработанный decline; если всегда — корень = падение интеграции. Плюс проверить, не создаётся ли битая/висящая подписка при 500.
- **Корреляция с OBS-01:** эндпоинт CloudPayments = вероятный источник варнингов `Unsupported PaymentOptions (sbpSupport)`; причинность не доказана.
- **Impact:** 5xx на монетизации нарушает DoD и алёртинг (alert fatigue на штатных decline), маскирует реальные инциденты, даёт риск мислида. Severity **High, не Critical**: пользовательский путь не сломан благодаря fallback фронта — поэтому NO-GO несёт BUG-01, а не BUG-03.

Это подтверждает корректность risk-based расстановки приоритетов.
